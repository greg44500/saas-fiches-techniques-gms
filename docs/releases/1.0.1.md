# Core 1.0.1 — Patch stable

**Version :** 1.0.1  
**Canal :** stable  
**Date :** 2026-09-18  
**Tag cible :** `v1.0.1`

## Objet

`1.0.1` corrige un écart de gouvernance découvert lors du bootstrap du premier SaaS métier réel dérivé de Core `1.0.0`.

Le contrat 1.0 indiquait déjà que la version applicative d’un SaaS dérivé devait rester indépendante de la version du Core. La gate `release:verify` ne disposait cependant d’aucun contrat machine-readable distinct pour porter cette identité produit sans détourner `core-release.json` ni reversionner les packages Core hérités.

## Changement observable

La séparation canonique est désormais :

```text
core-release.json
→ identité/version du Core

core-origin.json
→ provenance exacte du Core intégré dans le produit

product-release.json
→ identité/version applicative propre au produit dérivé
```

Un SaaS dérivé qui contient `core-origin.json` doit déclarer `product-release.json`.

Exemple :

```json
{
  "schemaVersion": 1,
  "name": "saas-example-product",
  "repository": "owner/saas-example-product",
  "version": "0.1.0",
  "channel": "development"
}
```

La version produit suit SemVer et les canaux `development`, `rc` et `stable`, indépendamment de la version Core.

Les `package.json` et lockfiles hérités restent alignés sur la version du Core. Un produit dérivé ne doit pas les renommer ou les reversionner uniquement pour porter son identité applicative.

## Upgrade d’un SaaS dérivé

L’intégration de `v1.0.1` doit suivre le flux habituel :

```text
git fetch upstream-core --tags
→ branche core-update/v1.0.1
→ merge du tag v1.0.1
→ revue du diff
→ création de product-release.json dans le produit
→ tests Core + métier + frontend + E2E
→ mise à jour de core-origin.json après validation
→ Pull Request produit
```

Important : l’arrivée du nouveau `release:verify` fera échouer la gate d’un dérivé contenant déjà `core-origin.json` tant que `product-release.json` n’aura pas été ajouté. C’est intentionnel afin que l’identité produit soit explicite.

## Rollback / reprise

En cas d’échec d’upgrade, ne pas fusionner la branche `core-update/v1.0.1` et conserver la provenance produit sur la dernière version Core validée.

Un tag publié n’est jamais déplacé.

## Contrôles post-publication

Après publication :

1. vérifier que `v1.0.1` cible exactement le commit `main` validé post-merge ;
2. vérifier que la GitHub Release est stable, non draft et non prerelease ;
3. vérifier `core-release.json` et les package/lockfiles à `1.0.1` ;
4. intégrer ensuite `v1.0.1` dans le premier produit réel via `core-update/v1.0.1`.
