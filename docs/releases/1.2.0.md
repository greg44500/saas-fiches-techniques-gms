# Core 1.2.0 — Application-global authorization

**Version :** 1.2.0
**Canal :** stable
**Date :** 2026-09-22
**Tag cible :** v1.2.0

## Objet

Core 1.2.0 ajoute une primitive générique d’autorisation métier globale pour les SaaS dérivés, indépendante du RBAC Platform et du RBAC Workspace.

Elle permet à un produit dérivé de gouverner des ressources métier globales sans détourner PlatformRole, Role ou WorkspaceMember.

## Ajouts backend

La release ajoute :

- applicationGlobalPermission.registry.js ;
- ApplicationGlobalRole ;
- ApplicationGlobalMember ;
- resolveApplicationGlobalAuthorization() ;
- authorizeApplicationGlobalPermission() ;
- services génériques de rôles et memberships ;
- anti-escalade ;
- bootstrap contrôlé ;
- AuditLogs dédiés ;
- migration d’index de production.

Le Core ne déclare aucune permission métier globale.

## Séparation des autorités

    Platform → administration interne du SaaS
    Application global → gouvernance métier globale du produit
    Workspace → autorisation tenant

Ces autorités sont cumulables par un même User mais ne s’impliquent jamais automatiquement.

Un super_admin Platform sans ApplicationGlobalMember ne reçoit aucun droit métier global.

## Sécurité

Les permissions effectives sont relues depuis MongoDB.

Le système échoue fermé pour un rôle archivé, un membership suspendu/révoqué, une permission persistée inconnue ou une permission réservée dans un rôle personnalisé.

Un acteur ne peut créer, modifier, attribuer ou administrer un rôle contenant des permissions qu’il ne possède pas.

## Frontend et HTTP

Aucune route métier ou interface frontend n’est ajoutée au Core.

Le SaaS dérivé reste responsable de ses routes, DTO et surfaces de gouvernance. Les routes dérivées utilisent authenticate puis authorizeApplicationGlobalPermission().

## Contrats DB

Deux nouvelles collections sont introduites :

    ApplicationGlobalRole
    ApplicationGlobalMember

Aucun document existant n’est modifié.

## Migration Core

Pre-deploy obligatoire avant utilisation de la primitive en production :

    npm run migration:application-global-authorization-indexes

Cette migration crée ou garantit les index des deux nouvelles collections.

## Migration produit dérivé

La migration Core ne crée aucun rôle métier.

Un produit qui utilise la primitive doit ensuite :

1. déclarer ses permissions dans le registre code-owned ;
2. synchroniser ses rôles système avec syncApplicationGlobalSystemRole() ;
3. bootstrapper explicitement le premier gouverneur avec bootstrapApplicationGlobalMember() si nécessaire.

## Variables d’environnement

Aucune variable ajoutée, supprimée ou modifiée.

## Dépendances

Aucune dépendance ajoutée, supprimée ou mise à niveau.

## Compatibilité

Aucun endpoint existant n’est supprimé, renommé ou modifié.

Les dérivés qui n’activent pas la nouvelle primitive conservent le comportement précédent.

## Upgrade d’un SaaS dérivé

    git fetch upstream-core --tags
    → branche core-update/v1.2.0
    → merge du tag v1.2.0
    → revue du diff
    → npm run migration:application-global-authorization-indexes
    → composition des permissions globales du produit
    → migration/seed produit des rôles et memberships
    → tests Core + métier + frontend + E2E
    → mise à jour de core-origin.json
    → Pull Request produit

Le produit ne doit pas déplacer ses permissions globales vers le namespace platform:.

## Rollback

Un tag publié ne doit jamais être déplacé.

Après création de données globales métier, un rollback doit préserver les nouvelles collections. Elles ne sont jamais supprimées automatiquement.
