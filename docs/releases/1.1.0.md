# Core 1.1.0 — WorkspaceMember transactional lifecycle

**Version :** 1.1.0  
**Canal :** stable  
**Date :** 2026-09-21  
**Tag cible :** `v1.1.0`

## Objet

`1.1.0` ajoute un point d’extension Core générique et rétrocompatible permettant à une application dérivée de participer atomiquement au retrait définitif d’un `WorkspaceMember`.

Le besoin démontré est celui d’une relation métier dérivée qui doit être invalidée lorsque le membership passe à `REMOVED`, sans introduire le modèle métier correspondant dans le Core.

## Nouveau contrat observable

Nouveau point de composition :

```text
backend/config/applicationWorkspaceMemberLifecycle.registry.js
```

Événement V1 :

```text
onMemberRemoved
```

Contexte transmis :

```text
workspaceId
membershipId
userId
actorId
session
ipAddress
userAgent
```

Le handler reçoit la session MongoDB active du Core et doit utiliser cette session pour ses écritures transactionnelles.

## Atomicité

Le retrait administratif suit désormais le contrat :

```text
WorkspaceMember -> REMOVED
→ handlers applicatifs onMemberRemoved
→ libération du quota members
→ AuditLog Core MEMBER_REMOVED
→ commit
```

La fermeture de compte utilisateur applique également ce lifecycle à chaque membership retiré.

Si un handler applicatif échoue, l’erreur est propagée au callback transactionnel. Le résultat attendu en base est un rollback de l’ensemble de la transaction.

## SUSPENDED et réinvitation

`SUSPENDED` ne déclenche pas `onMemberRemoved`.

La réactivation d’un membership historique `REMOVED` par le workflow d’invitation reste compatible avec le contrat existant. Le Core ne réactive aucune relation métier dérivée invalidée lors du retrait.

## Retries transactionnels

Les handlers applicatifs doivent rester déterministes et/ou idempotents dans la transaction MongoDB et ne doivent pas déclencher directement d’effets externes irréversibles.

À éviter dans un handler transactionnel :

```text
email immédiat
appel API externe non compensable
paiement
webhook non idempotent
```

Le cas d’usage attendu est une écriture MongoDB dérivée utilisant la `session` reçue.

## Compatibilité

La release est classée MINOR :

```text
1.0.1 → 1.1.0
```

Motif : nouvelle capacité Core rétrocompatible.

Une application dérivée qui n’enregistre aucun module WorkspaceMember lifecycle conserve le comportement antérieur.

Aucun endpoint HTTP existant n’est supprimé ou renommé.

## Sécurité

Cette évolution renforce la capacité d’un produit dérivé à maintenir atomiquement ses invariants d’accès lors d’un retrait définitif de membership.

Le Core ne connaît ni n’importe les modèles métier du produit dérivé.

## Upgrade d’un SaaS dérivé

Flux attendu :

```text
git fetch upstream-core --tags
→ branche core-update/v1.1.0
→ merge du tag v1.1.0
→ revue du diff
→ tests Core + métier + frontend + E2E
→ mise à jour de core-origin.json seulement après validation
→ Pull Request produit
```

Le simple upgrade rend le nouveau point d’extension disponible. L’enregistrement d’un handler métier reste une modification propre au produit dérivé et doit être réalisé dans son module métier, sur une branche distincte si la discipline du produit l’exige.

## Rollback / reprise

En cas d’échec d’upgrade d’un produit dérivé :

```text
ne pas fusionner core-update/v1.1.0
→ conserver la dernière provenance Core validée
→ corriger ou abandonner la branche d’upgrade
```

Un tag Core publié est immuable et n’est jamais déplacé.
