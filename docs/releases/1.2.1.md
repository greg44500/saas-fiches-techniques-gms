# Core 1.2.1 — Isolation des rate limits E2E

**Version :** 1.2.1
**Canal :** stable
**Date :** 2026-09-24
**Tag cible :** v1.2.1

## Objet

Core 1.2.1 corrige un défaut générique observé dans une suite Playwright dérivée : les scénarios fonctionnels pouvaient accumuler suffisamment d'appels depuis l'IP locale pour atteindre les quotas anti-abus du runtime et recevoir des réponses HTTP 429 sans rapport avec le contrat métier testé.

La correction introduit un bypass E2E explicite et sécurisé sans modifier les protections de production.

## Mécanisme

La nouvelle variable est :

    E2E_BYPASS_RATE_LIMITS=false

Elle reste désactivée par défaut.

Une valeur `true` n'est acceptée que lorsque les deux conditions suivantes sont réunies :

    NODE_ENV=test
    base MongoDB se terminant par _e2e_test

Toute activation en développement, en production ou sur une autre base MongoDB est refusée au démarrage par la validation Zod de l'environnement.

Le package Playwright Core active explicitement le flag dans `e2e/support/environment.js`.

## Rate limiters concernés

Le bypass sécurisé est appliqué aux limiteurs runtime actuels :

- API globale ;
- inscription par IP ;
- login par IP ;
- login par email pseudonymisé ;
- forgot-password par IP ;
- forgot-password par email pseudonymisé ;
- reset-password par IP ;
- acceptation d'invitation Workspace ;
- acceptation d'invitation Platform ;
- invitation commerciale.

Les middlewares restent montés. Ils utilisent un predicate `skip` partagé uniquement lorsque le contexte E2E validé est actif.

## Sécurité

La politique de production reste inchangée :

- aucun seuil n'est augmenté ;
- aucun retry HTTP 429 n'est ajouté ;
- aucun timeout Playwright n'est relevé pour masquer le problème ;
- `NODE_ENV=test` seul ne désactive aucun rate limiter ;
- les tests Vitest dédiés continuent à exercer les vrais compteurs ;
- les factories conservent l'injection de seuils faibles pour tester les réponses 429.

## Variables d'environnement

Ajout :

    E2E_BYPASS_RATE_LIMITS

Valeur par défaut :

    false

Le fichier `.env.example` documente le verrouillage du flag. Un environnement réel ne doit jamais l'activer.

## Contrats et données

Cette release ne modifie :

- aucun endpoint HTTP ;
- aucun payload ;
- aucune permission ;
- aucun modèle MongoDB ;
- aucun index ;
- aucune migration ;
- aucune dépendance.

## Validation de release

La gate canonique reste :

    npm run release:check

Elle couvre :

    release:verify
    lint backend/scripts/e2e
    tests backend
    lint frontend
    tests frontend
    build frontend
    E2E Playwright Core

La release ne doit être publiée qu'après succès réel de cette gate sur la PR et après validation post-merge conformément au processus habituel.

## Upgrade d'un SaaS dérivé

Après publication du tag `v1.2.1` :

    git fetch upstream-core --tags
    → branche core-update/v1.2.1
    → intégration du tag v1.2.1
    → revue du diff et de la nouvelle variable E2E
    → tests backend + frontend + build + E2E + release:verify
    → mise à jour de core-origin.json / provenance réellement utilisée
    → fusion de l'upgrade Core
    → remise à jour de la branche métier depuis main

Aucune migration MongoDB n'est nécessaire pour cette release.

## Rollback

Le changement n'altère aucune donnée persistée.

Un rollback code vers 1.2.0 réactive simplement le comportement précédent dans lequel les suites E2E consomment les quotas runtime. Aucun rollback DB n'est nécessaire.

Un tag publié ne doit jamais être déplacé.
